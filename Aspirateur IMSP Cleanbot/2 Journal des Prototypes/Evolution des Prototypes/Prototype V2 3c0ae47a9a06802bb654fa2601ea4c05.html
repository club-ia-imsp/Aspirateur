🎯 Objectifs de cette version

Le deuxième prototype représente une évolution majeure du projet, tant sur le plan mécanique qu'électrique. Les enseignements tirés du V1, notamment le manque de rigidité et la difficulté de maintenance liée au mélange des fonctions, nous ont conduit à envisager une refonte complète de la structure ainsi qu'une augmentation significative de la puissance d'aspiration.

🛠️ Détails de conception (Méca/Élec)

La structure a cette fois été imprimée en 3D, remplaçant le carton du V1 par du PLA pour obtenir une meilleure rigidité, une plus grande précision d'assemblage et une meilleure durabilité dans le temps. L'architecture a également été repensée en blocs distincts, avec d'un côté un bloc moteur et alimentation, et de l'autre un bloc de stockage des déchets séparé, ce qui a directement facilité la vidange et l'entretien de l’aspirateur par rapport au prototype V1.

Du côté de l’aspiration, l'équipe est passée d'un moteur unique à trois ventilateurs d'unité centrale couplés, assurant une aspiration nettement plus puissante et plus stable.

Enfin, un système d'allumage à distance du moteur d'aspiration a été ajouté, constituant la toute première étape du projet vers la connectivité totale via smartphone.

Concrètement, comment avons-nous procédé ?

Nous avons utilisé un ESP32 principalement à cause de son module Wi-Fi pour le contrôle à distance, et nous y avions joint un relais pour jouer le rôle de l'interrupteur qui actionnera à distance l'aspiration.

Au vu de cette séparation, nous avons maintenu, pour l'alimentation du bloc moteur de l'aspiration, la pile LiPo de 12V utilisée dans la phase 1.5.

Principe du montage : l'ESP32 ne pilote jamais directement le moteur d'aspiration. Il envoie un simple signal logique (HIGH ou LOW) à une broche de commande du module relais. Ce relais agit comme un interrupteur mécanique placé sur le circuit de puissance, entre la batterie LiPo 12V et le bloc moteur (les trois ventilateurs couplés). Fermer ou ouvrir ce circuit permet donc de démarrer ou d'arrêter l'aspiration à distance, sans jamais faire transiter le courant fort du moteur à travers l'ESP32 lui-même.

Exemple de code (serveur Wi-Fi minimal sur ESP32) :

#include <WiFi.h> // Bibliothèque standard de l'ESP32 pour gérer la connexion Wi-Fi

// À REMPLIR : indique ici le nom (SSID) et le mot de passe de ton réseau Wi-Fi
// L'ESP32 doit être sur le MÊME réseau que le smartphone qui enverra les commandes
const char* ssid = "NomDuReseau";
const char* password = "MotDePasse";

// Numéro de la broche GPIO de l'ESP32 physiquement reliée à l'entrée "IN" du module relais
const int relayPin = 26;
// Crée un petiterveur web sur le port 80 (port standard HTTP)
// C'est ce serveur qui va "écouter" les requêtes envoyées depuis le smartphone
WiFiServer server(80);
void setup() {
// Ouvre la communication série pour pouvoir suivre ce qui se passe
// dans le moniteur série de l'IDE Arduino (utile pour déboguer)
Serial.begin(115200);
// Indique à l'ESP32 que la broche du relais sera utilisée en SORTIE
// (l'ESP32 envoie un signal, il n'en reçoit pas sur cette broche)
pinMode(relayPin, OUTPUT);
// Sécurité : on force le relais à l'état "ouvert" (moteur éteint)
// dès le démarrage, pour éviter tout démarrage intempestif du moteur
digitalWrite(relayPin, LOW);
// Lance la tentative de connexion au réseau Wi-Fi défini plus haut
WiFi.begin(ssid, password);
// Tant que l'ESP32 n'est pas connecté, on attend et on affiche un point
// toutes les 500 millisecondes dans le moniteur série (juste pour voir la progression)
while (WiFi.status() != WL_CONNECTED) {
delay(500);
Serial.print(".");
}
// Une fois connecté, on affiche l'adresse IP attribuée à l'ESP32
// C'EST CETTE ADRESSE qu'il faudra utiliser depuis le smartphone
// (par exemple, l'appeler via un navigateur ou une appli : http://192.168.x.x/ON)
Serial.println(WiFi.localIP());
// Démarre effectivement le serveur, qui est maintenant prêt à recevoir des requêtes
server.begin();
}
void loop() {
// Vérifie si un appareil (le smartphone) essaie de se connecter au serveur
// Si personne ne s'est connecté, on ne fait rien et on recommence la boucle
WiFiClient client = server.available();
if (!client) return;
// Si un client est connecté, on lit la première ligne de sa requête
// (par exemple : "GET /ON HTTP/1.1")
String requete = client.readStringUntil('\r');
// On vide le reste de la requête qu'on n'a pas besoin de lire
client.flush();
// On regarde si la requête contient le texte "/ON" quelque part
// Si oui, cela signifie que l'utilisateur a demandé l'ALLUMAGE du moteur
if (requete.indexOf("/ON") != -1) {
digitalWrite(relayPin, HIGH); // ferme le relais → le circuit de puissance se ferme → le moteur démarre
// Sinon, on regarde si la requête contient "/OFF"
// Cela signifie que l'utilisateur a demandé l'EXTINCTION du moteur
} else if (requete.indexOf("/OFF") != -1) {
digitalWrite(relayPin, LOW); // ouvre le relais → le circuit de puissance se coupe → le moteur s'arrête
}
// Dans tous les cas, on renvoie une réponse HTTP basique au smartphone
// pour lui confirmer que la commande a bien été reçue et traitée
client.println("HTTP/1.1 200 OK");
client.println("Content-type:text/plain");
client.println();      // ligne vide obligatoire entre les en-têtes et le contenu
client.println("OK");  // le contenu renvoyé au client
// On ferme proprement la connexion avec ce client
// avant de revenir attendre la prochaine requête
client.stop();
}
Ce code fait fonctionner l'ESP32 comme un petit serveur web : une simple requête envoyée depuis le smartphone vers /ON ou /OFF active ou désactive le relais, et donc le moteur d'aspiration.

📊 Résultats des tests

Les tests ont révélé plusieurs difficultés qui ont nuancé les gains attendus de cette version.

Contrairement à ce qui était espéré, l'aspiration s'est révélée plus faible qu'avec le V1. Le passage à trois ventilateurs CPU couplés, pensé pour augmenter la puissance, a en réalité produit l'effet inverse : chaque ventilateur tirait l'air de son côté plutôt que de combiner leurs effets, ce qui a provoqué une baisse de la pression au niveau de la partie aspirante. À cela s'est ajoutée une légère fuite d'air au niveau de la jonction entre le bloc de stockage des déchets et le bloc moteur, cette jonction étant assurée par un simple serrage à vis, insuffisamment étanche.

Du côté de la commande électronique, le mécanisme fonctionnait globalement, mais la vitesse de déplacement s'est avérée trop élevée, et les directions avant, arrière, gauche et droite ne répondaient pas parfaitement. Nous soupçonnons ici un problème dans le code source fourni avec le kit robotique.

Les essais avancés ont également mis en évidence un problème lié à la taille de l'aspirateur, qui l'empêchait de se mouvoir dans des zones basses, comme sous les canapés. Le poids du prototype a par ailleurs constitué une difficulté supplémentaire.

Certains défis restaient donc à résoudre à l'issue de cette version : la gestion thermique des moteurs et la consommation énergétique globale, en plus des problèmes de pression d'aspiration, d'étanchéité, de précision de navigation, de gabarit et de poids identifiés ci-dessus.

💡 Améliorations pour la version suivante

Les problèmes identifiés sur le V2 ont directement orienté les objectifs du V3. Sur l'aspiration, il devenait nécessaire de repenser la configuration des ventilateurs pour qu'ils travaillent ensemble plutôt que de se contrarier, et de renforcer l'étanchéité de la jonction entre le bloc de stockage des déchets et le bloc moteur, notamment en révisant le système de fixation par vis.

Du côté de la mobilité, il fallait revoir la gestion de la vitesse de déplacement ainsi que la fiabilité des directions, en creusant en particulier l'hypothèse d'un problème dans le code source fourni avec le kit robotique. La question du gabarit et du poids du prototype restait également à traiter, afin de permettre à l'aspirateur de se déplacer dans des zones basses comme sous les canapés.

Enfin, les défis déjà connus de gestion thermique des moteurs et de consommation énergétique globale demeuraient d'actualité, tout comme l'ambition plus large d'une communication mobile complète et, à terme, d'une navigation automatique.
